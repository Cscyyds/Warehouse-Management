# Agent 小助手页面识别准确性优化方案

- 日期：2026-09-28
- 范围：前端 `wms-vue3/src/agent/`（第三方库 page-agent@1.12.2）
- 痛点定向：用户说一句话，Agent **跳错页面**或**匹配不到**（即"话术 → 目标页面/动作"链路，下称链路 B）
- 关联设计文档：`Page_Agent_Search.md`（2026-07-31，**已落后于代码**，见 §7）、`Page_Agent_WMS二次开发文档.md`
- 状态：**已实施（2026-09-28）**。按 §6 顺序全部落地，评测指标见 §8 实施结果

---

## 1. 背景与目标

### 1.1 现象

用户用自然语言下达指令后出现两类问题：

1. **跳错页**：请求被路由到了非预期页面（含"先跳 top1 再追问"策略造成的体感错跳，见 R2-④）
2. **匹配不到**：本地匹配失败后交给 LLM 盲猜，或落到澄清/无响应

### 1.2 目标

- 提升目标页面识别的 **top1 命中率**，降低 **错跳率**
- 建立**可量化评测基线**（当前完全没有，见 R6），使每次算法调整可回归、可验收

### 1.3 事实来源声明

本文档所有论断均来自以下之一，已逐条标注：
- 【实测】用 `node --experimental-strip-types` 直接运行 `navigationCatalog.ts` / `semanticIntentRouter.ts` 得到的真实输出（复现命令见附录 A）
- 【代码】源码位置（file:line）
- 【文档】两份设计文档（仅作背景，与代码冲突处以代码为准）

## 2. 现状链路拆解（链路 B）

入口：`agentRuntime.executeAgentTask(task)`（`agentRuntime.ts:380`），决策顺序：

```
用户话术
  │
  ├─ ① resolveDeterministicTaskIntent(task)          [semanticIntentRouter.ts:166]
  │    ├─ a. resolveLocalBusinessIntent(task)         [businessIntent.ts:200]
  │    │     14 类高特异正则 → confidence 0.96~0.98 → compileBusinessIntent 直连 Action
  │    │     门槛：decideIntentConfidence(minScore=0.85, minGap=0.15)  [semanticIntentRouter.ts:170-187]
  │    ├─ b. 通用正则快路径（40+ 条 pattern）          [semanticIntentRouter.ts:51-96 + 261-347]
  │    │     顺序敏感、先到先得；命中即返回 navigate / business-action
  │    ├─ c. findAgentNavigationCandidates(task, 8)    [navigationCatalog.ts:396]
  │    │     子串打分：正向 100+词长×10 / 反向 20+queryLen；excludedIntents 清零
  │    └─ d. decideIntentConfidence(minScore=120, minGap=15)  [intentConfidence.ts:16-38]
  │         confident → 导航/直连 Action；ambiguous → 跳 top1 + follow-up；insufficient → 澄清
  │
  └─ ② 未命中 → { kind: 'agent' } 交 LLM
       └─ LLM 依 getPageAgentInstructions() 注入的语义页面清单选页
            └─ navigate_wms_page(page, mode)            [navigationTool.ts:121]
                 └─ resolveAgentNavigation(pageName, mode)  [navigationCatalog.ts:351]
                      exact 命中 → 子串匹配 → 多命中报 ambiguous / 无命中报 not_found
```

### 2.1 打分规则细节（`navigationCatalog.ts:396-426`）

对每个页面，遍历 `title / aliases / keywords / synonyms` 全部词条：

| 匹配方向 | 条件 | 得分 |
|---|---|---|
| 正向包含 | `query.includes(term)` | `100 + term.length × 10` |
| 反向包含 | query 长度 ≥2 且 `term.includes(query)` | `20 + query.length` |
| 排除 | `excludedIntents` 命中 | 该页面分数清零 |
| 取值 | 所有词条取 **最大值**（不累计） | — |

置信度判定（`intentConfidence.ts:16`）：`minimumScore=120, minimumGap=15`。

### 2.2 已接入覆盖面（背景）

- 当前页面注册（链路 A）：15/64 白名单页面（10 个 view 文件；`PurchaseGenericList.vue` 以 `if (props.type)` 条件注册 6 个采购页）
- 白名单定义总数：`navigationCatalog.ts:72-156` 共 64 个页面

## 3. 根因分析（按严重度）

### R1【bug 级】注入 LLM 的语义清单被 URL 劫持 —— 这是"跳错页"最大的结构性根因

**机制**
- page-agent 的回调签名是 **`getPageInstructions?: (url: string) => ...`**，传入 URL 而非任务文本
  - 【代码】源码 `page-agent/packages/core/src/types.ts:66`；调用点 `PageAgentCore.ts:499-501`：`pageInstructions = instructions.getPageInstructions(url)?.trim()`
- WMS 侧 `instructions.ts:5` 把入参当作 task 使用：`getPageAgentInstructions(task?: string)` → `getAgentNavigationCatalogText(task)`（`instructions.ts:10`）

**实测结果**

| 传入 query | 候选数 | 注入内容 |
|---|---|---|
| URL（`http://localhost:5173/wms/sales/order`） | **0** | 全量 `id:title` 概览（1865 字符，无 description / 不适用 / 近义词 / 能力） |
| 任务文本（`昨天卖了什么货`） | 1 | 语义详述（202 字符/条，含"不适用：…；能力：…"） |

因 URL 不含中文与点分 ID（ID 里的 `.` 被归一化去掉、URL 里的 `/` 保留），`findAgentNavigationCandidates(url)` 实际**恒为空**。

**后果**
1. LLM 每步只看到 64 行 `sales.order:销售订单` 式索引，无法区分近义页面族：
   - 客户资料 / 新开拓客户 / 公海客户
   - 采购订单 / 采购入库单 / 采购退货单
   - 车辆管理 / 司机档案 / 物流公司
2. `instructions.ts:9` 的硬约束"'不适用场景'是硬约束"是**空指令**——该字段从未进入 Prompt
3. `semanticIntentRouter.ts:455` 注释"完整语义清单已由 getPageAgentInstructions 注入"的假设**不成立**
4. 本地 router 判定"交给 LLM"时（如候选歧义、无触发词），LLM 恰好处在信息最贫乏的输入下 → 跳错页/瞎猜

### R2 本地子串匹配对口语/简称/错别字零容错

**实测样例**（真实输出）

| 话术 | 候选（score） | 最终路由 |
|---|---|---|
| 员工信息 | system.personnel(140) | business-action ✓ |
| 查一下采购退货单 | purchase.return(150) | business-action ✓ |
| **看看车辆** | **（空）** | agent（交 LLM） |
| **查采退单** | **（空）** | agent（交 LLM） |
| 客户 | customer.info(120) 领先其余 22 分 | **agent**（无触发词） |
| 新增销售订单 | sales.order(140) | navigate ✓ |
| 哪些产品卖得最好 | （空） | business-action（靠硬编码正则兜住，`semanticIntentRouter.ts:298`） |

**暴露的四个缺陷**
1. **字段同权**：title 与 synonyms 同权；打分只看"最长匹配词条"，多词命中不累计、无覆盖率概念
2. **无容错**："车辆→车辆管理""采退→采购退货"这类简称/口语/错别字无法命中，仅靠硬编码正则逐个补（每个新说法都要改代码）
3. **excludedIntents 一票清零**（`navigationCatalog.ts:418`）：复合表达（如"公海客户退货"）可能被过度压制
4. **双门槛脱节**：候选打分（c/d）与触发词门槛（`navigationPattern/queryPattern`，`semanticIntentRouter.ts:52-53`）相互独立——"客户"案例中候选明确（gap=98）却因无触发词落到 LLM；反之，`ambiguous` 时"先跳 top1 再追问"（:365-384）会放大**排序不准**带来的错跳体感

### R3 正则快路径与语义目录形成双份事实来源

- 40+ 条正则（`semanticIntentRouter.ts:51-96, 261-347`）+ 14 类业务意图正则（`businessIntent.ts`）**顺序敏感、先到先得**
- 与语义目录（`navigationCatalog.ts` + `semanticCatalog/*`）内容重叠但不一致，新增页面/新说法要同时改两处
- 代码注释自认"匹配器眼瞎"（`semanticIntentRouter.ts:456`），是历次打补丁的痕迹

### R4 LLM 兜底通道的二次匹配脆弱（关联）

- LLM 传页面名后 `resolveAgentNavigation`（`navigationCatalog.ts:351-388`）只做 exact/子串匹配；LLM 用标题变体（如"采购单列表"）可能 `not_found`
- 多命中直接报 `ambiguous` 错误，**没有**本地链路那样的"top1 + 追问"兜底策略，容错度不对称

### R5 当前页面覆盖缺口（关联，影响"从哪出发"的上下文）

- 15/64 页面注册；`AddTemplate.vue`（`/common/add`，承载全部新增/编辑/详情表单）无任何 agent 代码
- 覆盖缺口对链路 A（"我在哪"）是独立问题，对链路 B 则是缺"出发点"上下文；建议作为后续阶段（§4 阶段 4）

### R6 无评测集（基础设施缺口）

- 现有 agent 相关测试共 1182 行（`src/agent/**/*.test.mjs`），全部是固定断言，**没有**"话术 → 期望页面"的数据集与准确率指标
- 任何算法/阈值调整目前都无法回答"变好了还是变坏了"

## 4. 优化方案（分阶段）

> 原则：先修 bug 级注入问题（半天、低风险）→ 建评测基线 → 再动匹配算法（用基线护航）→ 最后补覆盖与结构项。每阶段独立可回滚（纯前端改动）。

### 阶段 0：修复注入劫持（R1）—— 预计半天

**设计**

1. `agentRuntime.ts`：在 `executeAgentTask` 存入"最近任务文本"（模块级变量 + setter），任务执行期间不清除
2. `instructions.ts`：**忽略库传入的 URL 参数**，改用最近任务文本调用 `getAgentNavigationCatalogText`；同时用 `router.currentRoute` 直读当前路由，在 pageRegistry 未注册时也可补一句当前页面上下文
3. `navigationCatalog.ts`：注入格式改为 **"top6 语义详述 + 全量 id:title 索引"** 组合（当前实现是"有候选就只给候选"，需消除遮蔽风险）
4. 为注入文本加一个纯函数单测（断言包含 expected 页面的 excludedIntents / capabilities）

**预期收益**：LLM 侧输入从"64 行 id:title"升级为"6 条完整语义 + 64 条索引"；instructions 的"不适用场景"硬约束首次真正生效；近义页面族区分能力直接改善。

**成本**：每步 Prompt 增量约 1.2k 字符（可控）；不改变任何本地路由行为。

**风险**：page-agent 升级时回调签名若变更需同步（当前签名见附录 B）。

### 阶段 1：评测集与基线（R6）—— 预计 1-2 天

**数据设计**

```ts
interface IntentEvalCase {
  utterance: string            // 用户话术原样
  expectedPageId: string       // 期望页面（catalog id）
  expectedMode?: 'list' | 'create'
  expectedActionId?: string    // 期望直连 Action（若有）
  tags: string[]               // 如 ['简写', '口语', '近义页面', '多候选择一']
  source: 'existing-test' | 'field' | 'history' | 'synthetic'
}
```

**样本来源**（目标 120~200 条）
1. 现有测试用例反推（约 40 条）
2. 业务口语收集：车辆、采退单、开单、走货、欠款、滞销品等（按 R2 表格同型扩展）
3. 历史会话抽取（`agentUiStore` 会话记录，脱敏后入集）
4. 边界样本：空候选、多候选、近义页面族、各 section 主页兜底

**指标**

| 指标 | 定义 |
|---|---|
| top1 命中率 | `resolveDeterministicTaskIntent` 的页面/动作与期望一致 |
| top3 命中率 | 期望页面出现在候选前 3（含 ambiguous/insufficient 的候选列表） |
| 错跳率 | 本地路由到错误页面**且未追问**（最严重，优先压低） |
| 澄清率 | 落入 clarify / ask_user（过高说明覆盖率不足） |
| LLM 兜底率 | `kind: 'agent'` 占比（间接反映本地识别能力） |

**产物**：`scripts/agentIntentEval.mjs`（`node --experimental-strip-types`），每次运行输出 markdown 表格 + 混淆矩阵；纳入 npm script（如 `test:agent-intent-eval`）。

**注意**：阶段 1 只测**基线**，不调算法；阈值目标（如 top1 ≥ X%）由基线数值决定后再写入验收标准。

### 阶段 2：匹配算法升级（R2 / R3）—— 预计 2-3 天

**设计（替换 `navigationCatalog.ts` 的打分函数，语义目录成为单一事实来源）**

1. **字段权重**：title ×4、aliases ×3、keywords ×2、synonyms/intentExamples ×1.5（初始值，评测集回归校准）
2. **匹配升级**（分级启用，避免引入反向误配）：
   - L1 精确/子串（现状保留，最高分）
   - L2 拼音：全拼 + 首字母（"ccd" → "采购单"）。选型待定点①
   - L3 编辑距离 ≤ 2 容错（仅 2~4 字短词）
   - 多词命中累计（封顶），取代"只取最大值"
3. **excludedIntents 改为惩罚**（如最终分 ×0.3）而非清零，保留最小分阈值防误伤
4. **阈值联动**：新打分体系下用评测集网格搜索 `minimumScore / minimumGap`，并与触发词门槛（`navigationPattern/queryPattern`）合并评估（消除 R2-④ 的双门槛脱节）
5. **正则瘦身**：把已被语义目录完整覆盖的正则迁出（保留高特异案例），消除双份事实来源与顺序敏感问题

**验证**：评测集 top1/top3/错跳率对比阶段 1 基线；`npm run test:agent-output` 全绿。

**风险**：拼音/编辑距离可能引入误配 → 评测集量化 + "仅当 L1 无命中时启用"的分级策略兜底。

### 阶段 3：LLM 兜底通道加固（R1 剩余 / R4）—— 预计 1 天

1. 候选详述注入"可新增标记 + 能力 id"（字段已存在，确保进入 Prompt）
2. `resolveAgentNavigation` 的 `ambiguous` 从"报错"改为"Top1 + 提示候选"，或在 tool 返回中附候选清单让 LLM 自行追问（与本地链路策略对齐）
3. 页面名归一化复用阶段 2 的匹配器（含拼音/容错）

### 阶段 4：当前页面覆盖与一致性（R5，关联项）

1. `AddTemplate` 注册页面身份：`${type}.form` + mode 推导（设计参见 `Page_Agent_Search.md` §11.4.2；`mode: readonly=1→readonly / mode=edit→edit / 否则 create`）
2. **ID 一致性测试**：遍历 `navigationCatalog`，断言每个 `agentPageId` 都能在注册入口中找到（消除 `customer.info` vs `customer.info.list` 全靠人工对齐的风险，`pageRegistry.ts:62` 的 2.5s 超时会从运行时错误变为测试失败）
3. `useAgentPage` 支持响应式注册（watch key），消除 `PurchaseGenericList.vue:2074` 条件注册在 type 变化时不重注册的隐患

### 阶段 5（可选，结构）：Surface 栈

弹窗/抽屉识别（审核弹窗、详情抽屉），设计文档 §11.4.1 已有优先级栈方案但未实现。改动 `pageRegistry.ts` 引入活动 Surface 优先级。**本方案默认不纳入**，除非评测中发现"在弹窗内发起请求"是高频错配场景。

## 5. 待决策点（评审用）

| # | 决策点 | 选项 | 建议 |
|---|---|---|---|
| ① | 拼音匹配实现 | pinyin-pro 依赖（~30KB）vs 自建页面词表映射（~500 词） | 自建词表（依赖零新增、词条量可控）；若后续要泛化再引入库 |
| ② | 是否引入 BM25/向量召回 | 引入 vs 仅权重+拼音+编辑距离 | 先用轻量方案，评测集证明不足再引入；向量需后端配合，成本高 |
| ③ | ambiguous 策略 | 维持"先跳 top1 + 追问" vs 改为纯澄清 | 维持（产品决策"不要什么都不做"），但前提是阶段 2 排序准确率达标，否则错跳体感放大 |
| ④ | 正则去留 | 全量迁移到语义目录 vs 保留高特异正则 | 分两步：先补语义目录覆盖率，评测集验证等效后再删正则 |
| ⑤ | 评测集样本来源 | 是否从真实会话历史抽取（涉及脱敏） | 建议抽，但先过滤手机号/客户名（复用 `security/agentOutputSanitizer` 思路） |

## 6. 实施顺序与验收

| 阶段 | 内容 | 工作量 | 依赖 | 验证方式 |
|---|---|---|---|---|
| 0 | 修注入劫持（R1） | 0.5 天 | 无 | 注入文本单测 + 手工近义页面用例 |
| 1 | 评测集与基线（R6） | 1-2 天 | 阶段 0 可选并行 | 脚本输出基线报告 |
| 2 | 匹配算法升级（R2/R3） | 2-3 天 | 阶段 1 | 评测集对比（top1/错跳率）+ 现有测试全绿 |

| 4 | 覆盖与一致性（R5） | 1-2 天 | 无（可独立） | 一致性测试 + AddTemplate 冒烟 |

**建议验收标准（阈值待阶段 1 基线后填实）**
- 评测集错跳率 ≤ 基线值 − 50%（优先项，直接对应痛点）
- top1 命中率 ≥ 基线 + 15 个百分点
- `npm run test:agent-output` 与新增 eval 脚本全绿
- 手工场景清单（车辆/采退单/近义页面族/新增模式等 ≥ 10 条）逐条通过

# WMS 前端打包异常原因与修复策略

## 背景

在执行：

```powershell
npm run build
```

构建流程中的 `vue-tsc -b && vite build` 出现多轮 TypeScript（类型脚本）与 Vue 模板编译错误，导致打包中断。

本次文档用于整理：

- 打包失败的直接原因
- 每一类异常的根因
- 对应采用的修复策略
- 最终验证结果

---

## 打包流程说明

当前项目 `package.json` 中的构建命令为：

```json
"build": "vue-tsc -b && vite build"
```

这意味着构建分两步：

1. `vue-tsc -b`
   对 Vue 单文件组件和 TypeScript 类型进行检查
2. `vite build`
   在类型检查通过后，才正式输出 `dist`

因此，只要前一阶段存在类型或模板语法异常，打包就会直接失败，甚至还未进入 `vite build`。

---

## 第一轮异常

### 报错文件

- `src/views/product/ProductUnsold.vue`

### 报错现象

模板中如下写法导致 `vue-tsc` 报错：

```vue
{{ row.suppliers?.map((s: { supplier_name: string }) => s.supplier_name).join('、') || '-' }}
```

报错信息包括：

- `TS1005: ',' expected`
- `TS1128: Declaration or statement expected`
- `TS1005: ';' expected`

### 根因分析

问题不在业务逻辑本身，而在于：

- Vue 模板中的插值表达式 `{{ ... }}` 不适合直接内联复杂的 TypeScript 类型标注
- `vue-tsc` 在解析模板表达式时，遇到 `s: { supplier_name: string }` 会将其视为非法语法
- 所以虽然这段代码在语义上看似合理，但模板编译阶段无法通过

### 修复策略

采用“模板只负责展示，逻辑下沉到 `script setup`”的策略：

1. 将模板中的复杂拼接逻辑抽离为函数
2. 模板内只调用函数，不再写带类型标注的箭头函数
3. 为新增函数补充中文函数级注释，保持项目可维护性

### 修改结果

模板改为：

```vue
{{ formatSupplierNames(row.suppliers) }}
```

脚本中新增：

```ts
/**
 * 格式化供应商名称列表。
 * @param suppliers 供应商列表。
 * @returns 供应商名称使用顿号拼接后的文本，若为空则返回 `-`。
 * @example
 * formatSupplierNames([{ supplier_id: '1', supplier_name: '供应商A' }])
 */
function formatSupplierNames(suppliers?: SlowMovingItem['suppliers']) {
  return suppliers?.map((supplier) => supplier.supplier_name).join('、') || '-'
}
```

## 第二轮异常

第一轮问题修复后，重新执行打包，暴露出另外 4 个历史类型错误。

### 异常 1：销售退货单类型过宽

#### 报错文件

- `src/views/sales/SalesReturnSelectDialog.vue`

#### 报错现象

```vue
<li v-for="(item, idx) in selected" :key="item.sales_return_id" class="selected-item">
```

报错：

- `TS2322: Type 'unknown' is not assignable to type 'PropertyKey | undefined'`

#### 根因分析

`SalesReturnItem` 在 `src/api/legacy/sales.ts` 中原本定义为：

```ts
export interface SalesReturnItem { [k: string]: unknown }
```

这会导致：

- `sales_return_id` 被推断为 `unknown`
- Vue 里的 `:key` 只能接收字符串、数字或 symbol
- 因此类型检查失败

#### 修复策略

将模糊的索引签名类型，改为带明确核心字段的接口定义。

#### 修改结果

补全为：

```ts
export interface SalesReturnItem {
  sales_return_id: string
  return_no: string
  customer_name?: string
  return_amount?: string
  return_date?: string
  [k: string]: unknown
}
```

这样既保留了兼容性，也保证关键字段有明确类型。

---

### 异常 2：车辆列表返回字段使用错误

#### 报错文件

- `src/views/delivery/DeliveryTaskAdd.vue`
- `src/views/delivery/Vehicle.vue`

#### 报错现象

原代码中使用：

```ts
res.data.items
```

报错：

- `TS2339: Property 'items' does not exist on type 'VehicleListResponse'`

#### 根因分析

对照 `src/api/modules/vehicle.ts` 中的接口定义：

```ts
export interface VehicleListResponse {
  total: number
  page: number
  page_size: number
  vehicles: VehicleItem[]
}
```

可以确认：

- 真实字段名是 `vehicles`
- 组件里错误地把它当成了 `items`

#### 修复策略

严格以接口定义为准，将组件消费字段改为真实返回字段，避免前端“猜字段名”。

#### 修改结果

统一调整为：

```ts
res.data.vehicles
```

---

### 异常 3：客户搜索结果字段使用错误

#### 报错文件

- `src/views/sales/SalesReconciliationCreateDialog.vue`

#### 报错现象

原代码中使用：

```ts
(res.data.customers || []).map((c: any) => ({
```

报错：

- `TS2551: Property 'customers' does not exist on type 'CustomerListResponse'. Did you mean 'customer'?`

#### 根因分析

对照 `src/api/modules/customer.ts` 中的类型定义：

```ts
export interface CustomerListResponse {
  total: number
  page?: number
  page_size?: number
  customer: CustomerItem[]
}
```

可以确认：

- 真实字段为 `customer`
- 组件中误写成了 `customers`

#### 修复策略

1. 将字段名改为 `res.data.customer`
2. 顺手移除 `any`，改为显式使用 `CustomerItem`
3. 让映射过程和接口类型保持一致

#### 修改结果

改为：

```ts
customerOptions.value = (res.data.customer || []).map((c: CustomerItem) => ({
  customer_id: c.customer_id,
  customer_name: c.customer_name,
}))
```

## 采用的整体修复策略

本次没有采用“绕过报错”或“关闭检查”的方式，而是按以下原则逐项处理：

### 1. 优先修正真实类型，而不是弱化检查

- 没有关闭 `vue-tsc`
- 没有使用大面积 `as any`
- 没有通过跳过类型检查来强行生成 `dist`

### 2. 以接口定义为单一事实来源

- 所有返回字段都回到 `src/api/modules` 中核对
- 前端组件使用字段必须与接口定义一致

### 3. 复杂模板逻辑下沉到脚本层

- 模板只负责渲染
- 带类型推断、数组转换、字符串拼接等逻辑尽量抽离为函数

### 4. 最小改动修复

- 只改动出错字段和必要的类型定义
- 不随意重构无关代码
- 避免引入新的行为变化

## 最终结果

完成上述修复后，重新执行：

```powershell
npm run build
```

结果：

- `vue-tsc -b` 通过
- `vite build` 通过
- 成功生成 `dist`

当前仅剩一项非阻断性提示：

- `Some chunks are larger than 500 kB after minification`

这属于 Vite 的体积告警，不会阻止构建成功，也不影响当前上线。

## 结论

本次打包失败的根因主要分为两类：

- Vue 模板中直接书写了不被 `vue-tsc` 接受的 TypeScript 类型表达式
- 组件消费接口时使用了与真实返回类型不一致的字段名

最终通过以下方式完成修复：

- 将复杂模板逻辑抽离到脚本函数
- 补齐关键业务类型定义
- 按接口定义修正错误字段名
- 保持最小改动并重新验证打包

最终结果为：`npm run build` 已成功通过，项目可继续部署。
